L angChain Expression Language (LCEL) is a declarative way to easily compose chains together. It was designed from day one to support putting prototypes into production, with no code changes. It’s a key part of the LangChain toolkit and provides a fresh perspective on LLM-based application development.

Pre-requisites: Reader of this article must have basic understanding of LangChain framework and how it's used in GenAI application development.

Capabilities of LCEL

  • First-class streaming support: LCEL provides the best possible time-to-first token.
  • Async support: Any chain built with LCEL can be called both with the synchronous API and with the asynchronous API.
  • Optimized parallel execution: LCEL chains have steps that can be executed in parallel.
  • Retries and fallbacks: Configure retries and fallbacks for any part of your LCEL chain.
  • Access intermediate results: For more complex chains, it’s often very useful to access the results of intermediate steps even before the final output is produced.
  • Input and output schemas: Input and output schemas give every LCEL chain Pydantic and JSONSchema schemas inferred from the structure of your chain.
  • Seamless LangSmith tracing: As your chains get more and more complex, it becomes increasingly important to understand what exactly is happening at every step.
  • Seamless LangServe deployment: Any chain created with LCEL can be easily deployed using LangServe.

Advantages of LCEL

  • Faster POC to prod: LCEL supports putting prototypes into production, with no code change.
  • Custom chain creation: LCEL simplifies the process of creating custom chains with a new syntax.
  • Out of the box streaming and batch: LCEL gives you batch, streaming, and async capabilities for free.
  • Unified interface: It offers automatic parallelization, typing capabilities, and any future feature LangChain might develop.

Basic Components of LCEL

LCEL simplifies the construction of intricate chains using fundamental components and provides built-in features like streaming, parallelism, and logging.

In this process, the user input flows through a sequence of components: first to the prompt template, then to the model, and finally to the output parser. Let’s examine each component individually to gain a deeper understanding.

Pipe Operator ( Remember my Unix days :) )

The pipe symbol (|) functions similarly to a Unix pipe operator, connecting various components in a chain. It passes the output from one component as input to the next

Prompt

The prompt serves as a foundational blueprint, a BasePromptTemplate , that ingeniously transforms a dictionary of template variables into a PromptValue . This PromptValue elegantly encapsulates a fully formed prompt, ready to be utilized by either an LLM or a ChatModel . The LLM accepts a string as input, while the ChatModel operates on a sequence of messages. The versatility of the prompt lies in its ability to seamlessly interface with either type of language model, thanks to its inherent logic for generating BaseMessages and strings alike. This adaptability ensures a smooth and efficient operation, regardless of the language model type in use.

Model ​

The PromptValue is then passed to model . In this case our model is a ChatModel , meaning it will output a BaseMessage .

Output Parser

In the final stage of the process, we channel the output from our model into the output_parser . This output_parser is a BaseOutputParser , designed to accept either a string or a BaseMessage as input. The specialized StrOutputParser then steps in, effortlessly transforming any form of input into a string, showcasing its simplicity and efficiency.
